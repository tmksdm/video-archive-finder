## 1. Подтверждённая причина дефекта

### 1.1. Кратко

Дефект — **усечение выдачи до построения дерева**. Поиск физически находит 633
совпадения по запросу `фестиваль`, но пользователю доступны только 200 — причём
это 200 первых записей по внутреннему порядку, который не совпадает с
ожиданиями монтажёра. Файл
`10_15_ФестивальПамятиЕфремова_Лабецкая_03-23.mxf` находится в индексе, доступен
(`IsAvailable = 1`), но его позиция в этом порядке — 458-я из 606
совпадений по видеофайлам, поэтому он не попадает в окно. Контрольный запрос
`фестивальПамяти` сужает множество кандидатов и потому находит файл.

Иных причин потери совпадений в текущем индексе **не обнаружено**: все проверенные
«латентные» механизмы дают нулевой вклад (раздел 2.5). Три реально существующих, но
не проявляющихся сейчас дефекта индексации и очистки вынесены в отдельные задачи
(раздел 9) и в текущую реализацию не входят.

### 1.2. Цепочка кода

1. Жёсткая константа в модели представления, определяющая размер запроса:

   - `src/VideoArchiveFinder.Desktop/ViewModels/FolderSearchViewModel.cs:12` —
     `private const int MaximumDisplayedResults = 200;`
   - `src/VideoArchiveFinder.Desktop/ViewModels/FolderSearchViewModel.cs:185-190` —
     эта константа передаётся как `MaxResults` в `FolderSearchQuery`.

2. Отдельный `LIMIT` для папок и для видеофайлов:

   - `src/VideoArchiveFinder.Infrastructure/Search/SqliteFolderSearchService.cs:471` —
     `LIMIT $maxResults;` в запросе по `Folders`.
   - `src/VideoArchiveFinder.Infrastructure/Search/SqliteFolderSearchService.cs:244` —
     `LIMIT $maxResults;` в запросе по `VideoFiles`.
   - `src/VideoArchiveFinder.Infrastructure/Search/SqliteFolderSearchService.cs:85-108` —
     оба запроса выполняются независимо, затем результат объединяется.

3. Ограничение объединённого результата — уже **после** обоих `LIMIT`:

   - `src/VideoArchiveFinder.Infrastructure/Search/SqliteFolderSearchService.cs:322-342` —
     `MergeResults`: сначала идут все совпадения по папкам, затем по файлам,
     накопление прекращается при достижении `maxResults` (`:335-338`).
     Для воспроизведения это значит: 27 папок + 173 файла = 200, из бюджета
     выдачи 13,5 % расходуется на совпадения из **другого** источника.

4. Счётчик показывает усечённое число как общее:

   - `src/VideoArchiveFinder.Desktop/ViewModels/FolderSearchViewModel.cs:222-224` —
     `$"Найдено результатов: {matches.Count}"`, где `matches` — уже урезанный
     список. Отсюда «Найдено результатов: 200» в отчёте о дефекте.

5. Порядок, из-за которого «длинные» имена уходят за границу окна.
   Для видеофайлов (`SqliteFolderSearchService.cs:234-243`) и для папок
   (`:449-472`) сортировка одинаковая:

   ```
   CASE … END,                 -- приоритет: точное равенство → префикс → вхождение → прочее
   length(Name),               -- ← КОРОТКИЕ ИМЕНА ИДУТ ПЕРВЫМИ
   Name COLLATE NOCASE,
   Id
   ```

   Приоритетный класс здесь не разделяет совпадения: замер показал, что **все 606**
   найденных файлов имеют класс 2 (подстрока найдена, но не с начала имени). Поэтому
   фактически порядок определяет `length(Name)`: `10_15_ФестивальПамятиЕфремова_Лабецкая_03-23.mxf`
   имеет длину 48 символов, и перед ним оказывается 457 совпадений с более
   короткими именами.

6. Косвенное подтверждение того, что «просто увеличить константу» недостаточно:

   - `SqliteFolderSearchService.cs:13` — `MaximumAllowedResults = 1000`;
   - `SqliteFolderSearchService.cs:576-584` — значение `MaxResults` больше 1000
     отвергается с `ArgumentOutOfRangeException`;
   - `tests/VideoArchiveFinder.Tests/Search/SqliteFolderSearchServiceTests.cs:514-528` —
     это поведение закреплено тестом (`[InlineData(0)]`, `[InlineData(1001)]`).

   То есть потолок 200 задан в двух местах, и второй из них — «архитектурный»
   предел в сервисе.

### 1.4. Планы запросов и стоимость (измерено)

`EXPLAIN QUERY PLAN`:

```
-- поиск по видеофайлам
SEARCH v USING INDEX IX_VideoFiles_RootSourceId_FolderFullPath (RootSourceId=?)
SEARCH f USING COVERING INDEX UX_Folders_RootSourceId_FullPath (RootSourceId=? AND FullPath=?)
USE TEMP B-TREE FOR ORDER BY

-- поиск по папкам
SEARCH Folders USING INDEX IX_Folders_RootSourceId (RootSourceId=?)
USE TEMP B-TREE FOR ORDER BY
```

`instr()` не может использовать `IX_VideoFiles_NormalizedName`
(`SqliteVideoFileSchemaMigration.cs:65-70`), поэтому каждый запрос выполняет полный
проход по строкам источника и сортировку во временном B-дереве. **`LIMIT`
применяется уже после сортировки и не сокращает ни сканирование, ни сортировку.**

Замеры (медиана 10 прогонов после 5 прогревов, локальный файл индекса, тёплый кэш
ОС):

| Запрос | Медиана |
|---|---:|
| Страница видеофайлов, `LIMIT 200 OFFSET 0` (74 734 строки) | 40,27 мс |
| `COUNT(*)` по тому же условию | 39,34 мс |
| Страница папок, `LIMIT 200 OFFSET 0` (9 810 строк) | 4,08 мс |
| `COUNT(*)` по папкам | 5,40 мс |

Отсюда прямое следствие для проектирования: **страница и `COUNT` стоят одинаково**,
то есть честный общий счётчик удваивает стоимость одного цикла поиска.

## 2. Архитектурные ограничения текущего решения

### 2.1. Нормализация и морфология

- `TextNormalizationService` (`src/VideoArchiveFinder.Application/Search/TextNormalizationService.cs`):
  `FormC` → `trim` → `ToLowerInvariant` → `ё → е` → схлопывание пробелов.
  Дополнительно `Tokenize` делит строку по всем не-буквам/не-цифрам, поэтому
  `_`, `-`, `.` и цифры работают как разделители.
- `RussianSearchStemService` (`RussianSearchStemService.cs`): список окончаний плюс
  таблица «родственных» фрагментов; минимальная длина основы 3.
- Папки хранят предвычисленные `SearchTokens` и `SearchStems`
  (`SqliteIndexDatabaseInitializer.cs:209-210`), у видеофайлов таких колонок нет —
  «умный» поиск по файлам выполняет `instr` по `NormalizedName`
  (`SqliteFolderSearchService.cs:275-320`). На полноту текущей выдачи эта асимметрия
  не влияет, но означает, что любая индексная поддержка подстроки для файлов
  потребует отдельного решения (раздел 4.9).

### 2.2. Объединение папок и файлов

- Папки: `BuildSelectCommand` по таблице `Folders` (`:417-475`).
- Файлы: запрос с `INNER JOIN Folders` по `(RootSourceId, FullPath = FolderFullPath)`
  (`:212-245`), идентификатор результата — **отрицательный** `-v.Id` (`:215`),
  чтобы не пересекаться с положительными идентификаторами папок.
- `MergeResults` (`:322-342`) дедуплицирует по `Id`; поскольку пространства
  идентификаторов не пересекаются, схлопывания разных объектов не происходит.
  Порядок — «сначала папки, затем файлы», усечение — по общему счётчику.

Область поиска задаётся **двумя независимыми** наборами идентификаторов
(`FolderSearchQuery.RootSourceIds` и `VideoFileRootSourceIds`), которые
формируются в `MainWindowViewModel.UpdateSearchSourceFilter`
(`src/VideoArchiveFinder.Desktop/ViewModels/MainWindowViewModel.cs:707-732`) из
**объявленного режима индексации** каждого источника
(`ArchiveSourceIndexingMode`, `src/VideoArchiveFinder.Domain/ArchiveSources/ArchiveSourceIndexingMode.cs`).

Для постраничной выборки важно, что два потока упорядочены **независимо** и
объединяются «папки, затем файлы» — значит у каждого потока свой курсор, а общий
бюджет страницы распределяется между ними детерминированно (раздел 4.3).

### 2.3. Построение дерева

`FolderSearchTreeBuilder.Build`
(`src/VideoArchiveFinder.Application/Search/FolderSearchTreeBuilder.cs:15-93`):

1. словарь папок = контекстные папки (рекурсивный CTE
   `SqliteFolderSearchContextProvider.cs:54-115`, поднимающийся от
   `NavigationFolderId`/`Id` совпадения к корню) + сами совпадения (`:30-39`);
2. `FindIncludedFolderIds` (`:95-123`) добавляет всех предков каждого совпадения —
   поэтому в дереве есть узлы-«обёртки», которые не являются совпадениями
   (`IsMatch = false`);
3. дети раскладываются по `ParentFolderId`, корни и дети сортируются
   `Name OrdinalIgnoreCase`, затем `FullPath` (`:78-92`, `:140-160`);
4. узлы создаются рекурсивно с защитой от циклов (`:125-193`).

Ключевое ограничение: **`Build` принимает уже полный набор совпадений**. Он
вызывается ровно один раз на запрос
(`FolderSearchViewModel.cs:203-208`), и на его входе уже лежит усечённый список.
Модель «постепенной загрузки» в нынешнем виде не поддерживается — потребуется
инкрементальное добавление (раздел 4.7).

### 2.4. Виртуализация интерфейса

`SearchResultsTree` — `TreeView` с `VirtualizingPanel.IsVirtualizing="True"` и
`VirtualizationMode="Recycling"` (`MainWindow.xaml:844-854`),
`ScrollViewer.CanContentScroll="True"`. Шаблон иерархический
(`MainWindow.xaml:890-994`), состояние раскрытия задаётся **стилем контейнера**:
`<Setter Property="IsExpanded" Value="True"/>` (`MainWindow.xaml:877-888`).

Из этого следуют два вывода:

- Объекты узлов создаются **все сразу** в `FolderSearchTreeBuilder.Build`, до
  отрисовки: виртуализация панели сокращает число визуальных элементов, но не
  число объектов-узлов. При инкрементальной загрузке это ограничение снимается, но
  только если дерево перестать пересобирать целиком (раздел 4.7).
- Раскрытие не связано с данными. При пересоздании контейнеров раскрытие и
  прокрутка теряются, поэтому подгрузка страниц обязана **дописывать** узлы, а не
  пересобирать дерево. Это одновременно гипотеза о причинах наблюдения «видно
  только два файла» (раздел 8.3).

Также важно для совместимости: активация узла открывает папку в правой панели и
выделяет файл (`MainWindow.xaml.cs:1193-1233`), перетаскивание начинается с
`TryStartFolderDrag` (`MainWindow.xaml.cs:1301-1348`). Оба сценария работают с
`FolderSearchTreeNode` и должны быть сохранены (с учётом перехода на обёртку
представления, раздел 4.7.1).

### 2.5. Что проверено дополнительно и **не** является причиной дефекта

Каждый механизм проверен по индексу; вклад — нулевой (все значения измерены).

| Проверка | Результат | Вывод |
|---|---|---|
| Папки с `IsAvailable = 0` | 0 | нет пропусков из-за недоступных папок |
| Файлы с `IsAvailable = 0` | 0 | фильтр `v.IsAvailable = 1` (`:230`) ничего не отсекает |
| Файлы, чья папка отсутствует в `Folders` (теряются в `INNER JOIN`, `:226-228`) | 0 | соединение не теряет совпадений |
| `FolderIndexingStates.ErrorCount` для обоих действующих источников | 0 | индексация 2 октября 2026 прошла без ошибок |
| Папка `2025\10_ОКТЯБРЬ` | `IsAvailable = 1`, 386 файлов, 0 подпапок | доступна и проиндексирована |
| Дубликаты/пропуски в `MergeResults` | пространства `Id` не пересекаются | дедупликация не вредит |

## 3. Сравнение вариантов и гарантии пагинации

### 3.0. Общая база: что одинаково у всех вариантов

Измерение (раздел 1.4) показывает, что при текущих SQL-запросах **любая** схема
постраничной выдачи платит за полный проход по строкам источника и сортировку во
временном B-дереве: `instr()` и вычисляемый `CASE`-приоритет не индексируются.
Поэтому сравнивать варианты по «числу прочитанных строк» бессмысленно — оно
одинаково. Различаются они стоимостью позиционирования внутри отсортированного
результата и сложностью (а значит, и риском ошибки).

### 3.1. Вариант A. `OFFSET`/`LIMIT`

Тот же упорядоченный запрос, что и сегодня, плюс `LIMIT $pageSize OFFSET $n`.

Дополнительный замер, специально для оценки «страшного» `O(offset)`:

| Смещение | Медиана | Тип |
|---|---:|---|
| `OFFSET 0` | 40,18 мс | измерено |
| `OFFSET 2 000` | 41,13 мс | измерено |
| `OFFSET 20 000` | 42,16 мс | измерено |
| `OFFSET 50 000` | 40,16 мс | измерено |
| `OFFSET 73 000` | 40,05 мс | измерено |

Стоимость **плоская**: при 606 совпадающих строках сортировщик выдаёт 606 строк, и
пропуск любого их числа неразличим на фоне прохода по 74 734 строкам. Теоретический
недостаток `OFFSET` (линейный рост при глубоких страницах) для этого workload
**измерением не подтверждается**.

Плюсы: минимальные изменения; форма SQL совпадает с сегодняшней, то есть порядок
сортировки и фильтр переиспользуются дословно; никаких новых конструкций SQL и
связанных с ними тонкостей коллации.

Минусы: корректность требует неизменного индекса между страницами (раздел 3.4);
`OFFSET` не защищает от сдвига окна при мутации — но этот сценарий закрывается
политикой CHANGE-STOP, а не механизмом пагинации.

### 3.2. Вариант B. Keyset (seek) pagination

Условие «строго после курсора» по тому же кортежу, что и `ORDER BY`:

```sql
-- псевдокод
WHERE <условие поиска> AND <область> AND $hasCursor = 1
  AND (Priority, length(Name), Name COLLATE NOCASE, Id) > (?, ?, ?, ?)
ORDER BY Priority, length(Name), Name COLLATE NOCASE, Id
LIMIT $pageSize
```

Плюсы (реальные): ни дубликатов, ни пропусков в пределах неизменного индекса;
курсор — десятки байт, совпадения в памяти не удерживаются; при изменяющемся
индексе деградация мягче, чем у `OFFSET` (раздел 3.4).

Минусы (тоже реальные и именно в этом коде): стоимость страницы **та же**, что у
`OFFSET` (тот же проход и та же сортировка, что подтверждено измерением); требуется
CTE с вычисляемым `Priority`; сравнение кортежа из выражений обязано дословно
повторять `ORDER BY` вместе с `COLLATE NOCASE`, иначе часть совпадений молча
теряется — это тот самый класс дефекта, который мы устраняем. То есть keyset
добавляет самую опасную часть проекта, не давая измеряемого выигрыша.

### 3.3. Вариант C. Серверная «сессия поиска» с кешем совпадений

Один раз выполнить поиск, сохранить упорядоченный список кандидатов и отдавать
страницы срезом.

Плюсы: одна дорогая операция на запрос; простая выдача.

Минусы: 376 342 файла (замер 1 сентября 2026) при ~150-250 байтах на запись — это
десятки мегабайт на один запрос, что **прямо противоречит требованию 9** и плохо
сочетается с debounce: запросы создаются на каждый символ. Отклонён.

### 3.4. Гарантии при неизменном и при изменяющемся индексе

Ключ сортировки строки: `K = (Priority, length(Name), Name COLLATE NOCASE, Id)`.
`Id` уникален, поэтому `K` — тотальный порядок.

**A. Индекс не изменяется между страницами.** Оба варианта дают полную выдачу без
дубликатов и пропусков. Гарантия строгая и следует из тотальности порядка `K`.

**B. Индекс изменяется между страницами.** Гарантий полной выдачи нет ни у одного
из вариантов — это важно зафиксировать честно. Различаются виды отказа:

| Событие | `OFFSET` | Keyset |
|---|---|---|
| Вставка строки **до** текущего окна | окно сдвигается: часть строк показывается дважды, часть пропускается | строка не появится (пропуск), дубликатов нет |
| Вставка строки **после** окна | как правило, появится на последующих страницах | появится на последующих страницах |
| Удаление строки, уже показанной | остаётся в дереве как устаревший узел | то же |
| Удаление строки до её страницы | окно сдвигается: дубликаты и пропуски | строка просто не приходит |
| Изменение `K` строки после её показа (переименование) | дубликаты и пропуски у всех сдвинувшихся строк | **дубликат** именно этой строки |
| Изменение `K` строки до её страницы | дубликаты и пропуски | строка может быть пропущена |

Итог: keyset строго устойчивее — у него деградируют только строки, у которых
изменился собственный ключ сортировки, тогда как `OFFSET` при любой мутации до окна
портит окно целиком. Но **ни один из вариантов не даёт полноты**, поэтому
корректность должна обеспечиваться не механизмом пагинации, а политикой ниже.

### 3.5. Политика CHANGE-STOP (строгое поведение при изменении индекса)

Принятое поведение фиксируется однозначно:

1. В начале постраничного поиска снимается отпечаток состояния индекса `S0`
   (раздел 4.5) и он запоминается вместе с сессией поиска.
2. Перед выполнением каждой следующей порции отпечаток снимается заново — **в той
   же транзакции чтения**, что и сама порция.
3. Если отпечаток отличается от `S0`:
   - порция **не выполняется**;
   - дальнейшая подгрузка **прекращается**; кнопка «Показать ещё» блокируется и
     заменяется предложением обновить результаты;
   - **уже построенное дерево остаётся на экране без изменений** — ни один
     показанный узел не удаляется, не переставляется и не переоткрывает раскрытие;
   - пользователю показывается подсказка «индекс изменился — обновить результаты»;
   - единственный способ продолжить — запустить поиск заново (это сбрасывает `S0`,
     дерево и счётчики).
4. Смена запроса, режима или набора источников равносильна новому поиску и всегда
   начинает новую сессию.

Что гарантирует политика:

- **Пока подгрузка не остановлена, индекс тождествен состоянию на момент первой
  порции** (отпечаток снимается в одной транзакции с порцией, а изменение приводит к
  остановке). В этих условиях выдача **полная**: ни одна строка не показана дважды и
  ни одна не пропущена — строгая гарантия, а не «как правило».
- Отпечаток на `PRAGMA data_version` строго возрастает при каждом изменении файла
  базы другим соединением, поэтому пропустить изменение нельзя даже в случае, когда
  состав строк вернулся к прежнему виду.
- Устаревшие результаты не появляются на экране (требование 7) — уже при первом
  обнаружении изменения.
- Уже показанное дерево никогда не «перетасовывается» под курсором.

Цена политики: при изменении индекса пользователь видит подсказку и должен обновить
результаты, даже если изменение не затронуло его запрос (ложное срабатывание,
раздел 4.5.4). Это сознательный обмен точности на простоту и предсказуемость.

### 3.6. Сравнение и окончательная рекомендация

| Критерий | A. `OFFSET`/`LIMIT` | B. Keyset | C. Сессия с кешем |
|---|---|---|---|
| Полнота при неизменном индексе | да | да | да |
| Полнота при изменяющемся индексе (без CHANGE-STOP) | дубликаты и пропуски у всего окна | дубликаты/пропуски только у строк со сменой ключа | нет |
| Полнота при изменении (с CHANGE-STOP) | да, подгрузка останавливается | да, подгрузка останавливается | не требуется |
| Стоимость страницы | 40,3 мс (измерено) | 40,3 мс (измерено, тот же проход) | O(1) + память |
| Стоимость при глубокой странице | плоская до `OFFSET 73 000` (измерено) | плоская | O(1) |
| Память на все совпадения | нет | нет | десятки МБ — нарушает требование 9 |
| Новый риск ошибки в SQL | низкий (форма запроса та же) | высокий (повтор выражений и коллации) | низкий |
| Объём изменений | малый | средний | средний |

**Окончательная рекомендация — вариант A, `OFFSET`/`LIMIT`, вместе с политикой
CHANGE-STOP.**

Это изменяет рекомендацию первоначального документа (там был выбран keyset). Причины
изменения:

1. Измерение показало, что выигрыша в скорости у keyset нет: оба варианта платят
   одинаковый полный проход и сортировку, а стоимость `OFFSET` плоская — вплоть до
   смещения 73 000 при 606 совпадениях.
2. Единственное реальное преимущество keyset — более мягкая деградация при
   изменяющемся индексе — **нейтрализуется политикой CHANGE-STOP**, которая нужна в
   любом случае и которая даёт более сильную гарантию, чем любой из механизмов по
   отдельности.
3. Keyset добавляет самую рискованную часть проекта (дублирование выражений
   сортировки и правила коллации), а именно расхождение выражений даёт ровно тот
   дефект — молчаливую потерю совпадений, — от которого мы избавляемся.

**Keyset остаётся запасным вариантом** и должен быть выбран только при выполнении
измеримого триггера: если замер на 350 000+ файлов (раздел 7) покажет, что
стоимость страницы растёт с номером страницы настолько, что p95 последней страницы
превышает согласованный порог. Тогда реализуется вариант B за отдельным
утверждением, вместе с обязательным тестом эквивалентности порядков.

## 4. Рекомендуемая архитектура

### 4.1. Новый контракт вместо изменения существующего

Чтобы не ломать 255 существующих тестов и вызовы, добавляется постраничный
контракт, а старый становится его частным случаем.

```
Application/Search/FolderSearchSession.cs      // отпечаток S0, курсоры потоков,
                                               // счётчики, пределы страницы
Application/Search/FolderSearchPage.cs         // Matches, TotalMatchCount,
                                               // LoadedMatchCount, HasMore,
                                               // FolderMatchCount, VideoMatchCount,
                                               // NextOffset, IndexChanged
Application/Search/IFolderSearchPageService.cs
Infrastructure/Search/SqliteFolderSearchPageService.cs
```

- `IFolderSearchService.SearchAsync` остаётся и реализуется как «первая страница
  с `MaxResults`» через новый сервис — поведение и тесты сохраняются.
- Общие построители SQL (условие «умного» поиска, элементы `ORDER BY`,
  параметризация источников) выносятся в один внутренний помощник, чтобы условия
  поиска и порядок физически не могли разойтись между «точечным» и постраничным
  запросами. Для варианта A это дешевле, чем для keyset, но ценность сохраняется:
  одинаковый порядок обязан использоваться и в выдаче, и в `COUNT`.

### 4.2. Постраничный запрос

Форма запроса остаётся сегодняшней, добавляются только `OFFSET` и распределение
бюджета между двумя потоками:

```sql
SELECT … FROM Folders
WHERE <условие поиска> AND RootSourceId IN (…)
ORDER BY <тот же ORDER BY, что и сейчас>
LIMIT $limit OFFSET $offset;
```

Видеофайлы — та же форма с `v.Name`, `v.NormalizedName` и `INNER JOIN Folders`.
Отдельным запросом считается общее число совпадений по каждому потоку (`COUNT`
с тем же условием и той же областью, без `ORDER BY` и без соединения — измерено,
что соединение на стоимость не влияет: 39,34 мс против 40,39 мс).

### 4.3. Распределение бюджета страницы между потоками

Порядок выдачи сохраняется как сегодня — «сначала папки, затем файлы»:

- у каждого потока собственные `offset` и `limit`;
- страница набирается так: `folderTake = min(pageSize, folderTotal - folderLoaded)`,
  остаток бюджета `pageSize - folderTake` берётся из потока файлов
  (`videoTake = min(pageSize - folderTake, videoTotal - videoLoaded)`);
- `HasMore = folderLoaded < folderTotal || videoLoaded < videoTotal`.

При 27 совпадениях по папкам это вырождается в чистую постраничную выдачу файлов,
а поведение первой страницы полностью совпадает с сегодняшним. Требование 6
(совместное объединение совпадений по папкам и файлам) выполняется структурно, а не
сортировкой двух выборок между собой.

### 4.4. Счётчики

Модель представления получает:

- `TotalMatchCount` — точное общее число совпадений (из `COUNT`), требование 2;
- `LoadedMatchCount` — сколько совпадений уже показано (требование 5 ревью);
- `HasMoreResults` — есть ли следующая порция;
- `ResultsSummary` — «Найдено совпадений: 633; показано 200».

### 4.5. Отпечаток состояния индекса (`IndexStamp`)

#### 4.5.1. Почему прежний вариант отвергнут

В первоначальном документе предлагалось `MAX(CompletedAtUtc)` из
`FolderIndexingStates` плюс `MAX(LastSeenUtc)` по `VideoFiles`. Проверка по путям
записи показала, что этого **недостаточно**:

| Событие | Пишет | Видит прежний отпечаток? |
|---|---|---|
| Завершение полного обхода источника | `FolderIndexingStates.SaveAsync` (`FolderIndexingService.cs:269-288`), `LastSeenUtc` в `Folders`/`VideoFiles` | да |
| Открытие папки (догрузка имён файлов) | `VideoFolderRefreshService` → `UpsertBatchAsync`, `LastSeenUtc = now` | да, если новая метка больше текущего максимума |
| Удаление устаревших файлов папки | `CompleteFolderScanAsync` — только `DELETE` (`SqliteVideoFileIndexRepository.cs:536-595`) | **нет**: ни одна метка не растёт |
| Удаление устаревших папок | `CompleteScanAsync` — только `DELETE` (`SqliteFolderIndexRepository.cs:102-349`) | **нет** |
| Переименование файла | вставка новой строки + последующее удаление старой | вставка видна, если метка больше максимума; удаление — нет |
| Обновление одного файла на месте | `UPDATE` с новой `LastSeenUtc` | да |
| Удаление источника | `DeleteByRootSourceIdsAsync` — только `DELETE` | **нет** |

Кроме того, удаление строки, у которой метка была максимальной, **уменьшает**
`MAX(LastSeenUtc)`, то есть отпечаток может измениться «в обратную сторону» и
совпасть со значением из другой точки времени.

#### 4.5.2. Предлагаемый механизм

**`PRAGMA data_version` на сессионном соединении.** SQLite увеличивает это значение,
когда файл базы изменила **любая другая** транзакция или соединение. Это ровно наш
случай: сессия поиска читает, все изменения приходят от пишущих соединений
приложения.

- Сессия поиска держит одно открытое read-only соединение на время жизни сессии
  (пока результаты на экране).
- `S0` снимается при создании сессии, текущее значение — перед каждой порцией.
- Любое расхождение означает остановку подгрузки (раздел 3.5). Это **единственный
  источник решения**; никакие другие проверки не могут отменить остановку.
- Никаких сканов, никаких эвристик по времени и количеству строк, **изменение схемы
  индекса не требуется**.

#### 4.5.3. Проверка семантики (измерено)

Поведение проверено экспериментально на отдельной временной базе в `%TEMP%`
(рабочий индекс пользователя не изменялся): read-only соединение-читатель и
отдельное соединение-писатель.

| Действие другого соединения | `data_version` изменился | Тип |
|---|---|---|
| `INSERT` + commit | да (1 → 2) | измерено |
| `DELETE` + commit | да (2 → 3) | измерено |
| `UPDATE` + commit | да (3 → 4) | измерено |
| `INSERT` + `DELETE` в одной транзакции (число строк не изменилось) | да (4 → 5) | измерено |
| соединение-читатель остаётся работоспособным | да | измерено |
| прагма работает в режиме `mode=ro` | да | измерено |

То есть механизм одинаково надёжно ловит вставку, удаление, обновление и даже
изменение с нулевым итогом по числу строк — все те случаи, где прежний отпечаток
молчал. Временная база удалена после проверки.

#### 4.5.4. Ложные срабатывания и роль тройки `(COUNT, MAX(Id), MAX(LastSeenUtc))`

`data_version` меняется при **любом** изменении файла, включая переиндексацию
источника, не участвующего в запросе. Тогда CHANGE-STOP остановит подгрузку
напрасно: результаты по неизменившимся источникам остаются валидными. Ложное
срабатывание допустимо — оно стоит пользователю одной повторной команды поиска, а
переиндексация при открытых результатах редка.

Дополнительно можно вычислить тройку `(COUNT(*), MAX(Id), MAX(LastSeenUtc))` по
участвующим в запросе источникам — **только для диагностики** (какой источник
изменился, запись в журнал), не для отмены остановки. Тройка дешева и объяснима:

- вставка всегда увеличивает `MAX(Id)` (идентификаторы `AUTOINCREMENT` монотонны);
- удаление всегда уменьшает `COUNT(*)`;
- обновление на месте в текущих путях записи всегда увеличивает `LastSeenUtc`
  (записи всегда используют `DateTimeOffset.UtcNow` на старте обхода или открытия
  папки);
- любое изменение состава строк обнаруживается: вставка поднимает монотонный
  `MAX(Id)`, удаление уменьшает `COUNT(*)`, а взаимно отменяющая пара «вставка +
  удаление той же строки» оставляет таблицу тождественной и потому не требует
  обнаружения.

Стоимость тройки (измерено, медиана 10 прогонов):

| Запрос | Медиана |
|---|---:|
| `Folders`, источник `\\archive2` (672 строки) | 0,09 мс |
| `VideoFiles`, источник `\\archive2` (74 734 строки) | 27,43 мс |
| `Folders`, источник `\\archive1` (9 810 строк) | 2,82 мс |
| `VideoFiles`, источник `\\archive1` (12 306 строк) | 6,83 мс |

То есть тройка стоит около 37 мс и вычисляется только при срабатывании сторожа — и
только для диагностики.
План запроса подтверждает использование индексов
(`IX_Folders_RootSourceId`, `IX_VideoFiles_RootSourceId_FolderFullPath`), но
`COUNT(*)` всё равно проходит по всем строкам источника — это и объясняет 27 мс.

Тройка **не является второй линией обороны и не должна подавлять остановку**. Если
бы результат уточнения («состав строк не изменился») отменял срабатывание сторожа,
пропуск изменения стал бы возможен при отказе допущений (а) или (б), то есть
вернулась бы ровно та деградация пагинации, от которой мы ушли. Поэтому:

- **остановка подгрузки выполняется по `data_version`, безусловно**;
- тройка используется только как диагностика — чтобы показать, какой источник
  изменился, и, при желании, записать это в журнал;
- тесты обязаны проверять именно безусловность остановки, а не «уточнённый» вердикт.

Остаточные допущения уточнения (для диагностики, не для решения): монотонность `Id`
и то, что `LastSeenUtc` записи всегда больше предыдущего максимума.

Если держать сессионное соединение признают нежелательным, остаётся **только**
вариант с тройкой как единственным механизмом. Тогда гарантия становится условной:
полнота обеспечивается лишь при выполнении допущений (а) и (б), а стоимость растёт
(37 мс на каждую порцию плюс 40 мс на порцию и 40 мс на `COUNT`). Это альтернатива,
требующая отдельного утверждения, а не рекомендуемый путь.

### 4.6. Чтение в одной транзакции

Отпечаток и порция читаются в **одной** транзакции чтения, чтобы снимок был
согласованным. Транзакции короткие (десятки миллисекунд), `busy_timeout = 5000` уже
установлен. База работает в `journal_mode = delete` (измерено), поэтому длинная
транзакция чтения может задерживать писателя — ещё одна причина держать её короткой.

### 4.7. Инкрементальное дерево

Полный набор совпадений больше не передаётся в `Build`: после первой порции дерево
только **дополняется**. Это снимает ограничение раздела 2.3 и выполняет требование 9
(в памяти находятся только загруженные узлы).

#### 4.7.1. Мутабельная модель представления

`FolderSearchTreeNode` — неизменяемая запись уровня Application, и пересобирать её на
каждую порцию нельзя: пересборка пересоздаёт контейнеры и теряет раскрытие и
прокрутку. Поэтому вводится **обёртка представления** (слой Desktop):

```
FolderSearchTreeItem  : INotifyPropertyChanged
    IsMatch           { get; set; }        // монотонно: false → true
    NameSegments      { get; set; }        // пересчитывается при переклассификации
    Children          ObservableCollection<FolderSearchTreeItem>
    DirectSubfolderCount / DirectVideoFileCount
    + неизменяемые Id, FullPath, Name, RootSourceId, IsVideoFile,
      NavigationFolderId, NavigationFolderFullPath
```

`FolderSearchTreeNode` (Application) остаётся без изменений и продолжает
использоваться `FolderSearchTreeBuilder` и его тестами; обёртка создаётся при
преобразовании. Затрагиваются только локальные места Desktop: шаблон дерева,
`MainWindow.xaml.cs:1193-1233` (активация узла) и `:1301-1348` (перетаскивание).

#### 4.7.2. Порядок, раскрытие, виртуализация, прокрутка

- **Порядок.** Дети сортируются тем же компаратором, что и в `Build`
  (`Name OrdinalIgnoreCase`, затем `FullPath`). Следствие, которое нужно принять
  сознательно: новая порция может вставить узел **в середину** уже отрисованного
  списка детей, потому что порядок совпадений в выдаче не совпадает с алфавитным
  порядком дерева. `ObservableCollection` это поддерживает; панель перестраивает
  разметку, содержимое может сдвинуться. Автопрокрутка не выполняется.
  Альтернатива — упорядочивать детей по порядку поступления (только дописывание в
  конец), но это меняет нынешнее видимое поведение и ломает существующие тесты
  порядка, поэтому по умолчанию отвергается и выносится в открытые вопросы.
- **Раскрытие.** `IsExpanded` задаётся стилем контейнера (`MainWindow.xaml:877-888`),
  поэтому новые контейнеры создаются раскрытыми — и вновь добавленные ветви, и
  созданные при дописывании цепочки предков. Пока родительские контейнеры не
  пересоздаются, раскрытие сохраняется.
- **Виртуализация.** Дописывание в `ObservableCollection`, привязанную к
  виртуализированному `TreeView`, поддерживается. Порция добавляется **одним пакетом
  на UI-потоке**, без промежуточных перерисовок; `Results.Clear()` после первой
  порции не вызывается никогда.
- **Прокрутка.** Так как дерево не пересобирается, позиция прокрутки сохраняется.
  Новые узлы появляются выше или ниже текущей позиции без перехода к ним.
- **Известный риск раскрытия при переработке контейнеров** (виртуализация с
  `VirtualizationMode="Recycling"` и раскрытие, заданное стилем) — существующая
  проблема, не создаваемая этой задачей; при инкрементальной загрузке она становится
  заметнее. Проверка и возможный перенос `IsExpanded` в модель узла — пункт 7.2 и
  открытый вопрос 8.3.

#### 4.7.3. Переклассификация контекстного узла в совпадение

Требование ревью: папка может сначала появиться как **контекстный узел**
(`IsMatch = false`, добавлен как предок совпадения), а на следующей порции прийти
как **самостоятельное совпадение по имени папки**. Обрабатывается так:

1. узел ищется по `Id` в уже построенном дереве (индекс `Id → узел`);
2. если найден — обновляется **in place**: `IsMatch = true`, `NameSegments`
   пересчитываются через `FolderNameHighlightService.CreateSegments(name, queryText,
   mode)` (тот же вызов, что и в `FolderSearchTreeBuilder.CreateNode:164-174`),
   `DirectSubfolderCount`/`DirectVideoFileCount` берутся из пришедшего результата;
3. идентичность узла и его `Children` сохраняются — контейнер не пересоздаётся,
   раскрытие и выделение не теряются;
4. если не найден — создаётся новый узел как совпадение вместе с цепочкой предков.

Обратный порядок (совпадение пришло раньше, контекст позже) обязан быть безопасным:
`IsMatch` **монотонен** — контекстный узел никогда не понижает уже установленный
`IsMatch = true` и не затирает подсветку. Это правило — ключевое в `Merger` и
закрепляется отдельным тестом.

#### 4.7.4. Свойства, закрепляемые тестами

Идемпотентность (повторное применение той же порции не меняет дерево и не создаёт
дубликатов); эквивалентность одноразовому `Build` при любом разбиении на порции;
группировка «источник → год → месяц → папки» при попадании файлов одной папки в
разные порции; переклассификация контекстного узла; монотонность `IsMatch`; создание
цепочки предков ровно один раз; сохранение порядка детей.

### 4.8. Отмена, версионирование и офлайн

- Механизм `_searchVersion` + `CancellationTokenSource` уже реализован
  (`FolderSearchViewModel.cs:112-173`, `:210-213`, `:226-229`). Он распространяется
  на порции: загрузка несёт версию, результат устаревшей версии не добавляется в
  дерево (требование 7), а сама сессия поиска при смене версии закрывается вместе со
  своим read-only соединением.
- Подгрузка порции выполняется асинхронно, без блокировки UI; на время загрузки
  кнопка блокируется, дерево остаётся отзывчивым (требование 3).
- Поиск обращается только к локальному файлу SQLite, сеть в пути поиска не
  участвует. Рекомендуется перевести соединение поиска с `ReadWriteCreate`
  (`SqliteFolderSearchService.cs:495-509`) на `ReadOnly`: сейчас поиск открывает базу
  на запись и **создаёт пустую базу**, если файл потерян. Провайдер контекста уже
  работает в `ReadOnly` (`SqliteFolderSearchContextProvider.cs:159-173`). Требование 8
  дополнительно закрепляется тестом: поиск по существующему локальному индексу
  работает при недоступном UNC-пути источника.

### 4.9. Производительность: измеренное, экстраполяция, неизмеренное

**Измерено** (16 октября 2026, локальный файл индекса, тёплый кэш ОС, медиана
10 прогонов):

| Показатель | Значение | Условия |
|---|---:|---|
| Проход по 74 734 строкам + сортировка, страница 200 | 40,27 мс | источник `\\archive2`, запрос `фестиваль` |
| То же со смещениями до 73 000 | 40,05-42,16 мс | стоимость плоская |
| `COUNT(*)` с условием | 39,34 мс | без соединения и сортировки |
| Проход по 9 810 строкам, страница 200 папок | 4,08 мс | источник `\\archive1` |
| `COUNT(*)` по папкам | 5,40 мс | |
| Тройка-диагностика отпечатка (по запросу, только при срабатывании сторожа) | ~37 мс | 0,09 + 27,43 + 2,82 + 6,83 мс |
| `PRAGMA data_version` | ниже разрешения замера | одна прагма, без сканов |
| Построение полного дерева из 633 совпадений | не измерялось отдельно | вне поиска, в UI-потоке |

Отсюда **измеренный** вывод: цикл «страница + точный счётчик» стоит около
80 мс на текущем индексе по самому крупному источнику. Это уже близко к
действующему порогу p95 ≤ 100 мс из
`tools/VideoArchiveFinder.SearchBenchmark/SearchPerformanceBaseline.md`, причём
прежний замер этого не показывает: в нём нет видеофайлов вообще (только папки и
лимит 200 — 35-46 мс).

**Экстраполяция** (не подтверждена, решением не является): замер 1 сентября 2026
фиксирует 376 342 видеофайла, то есть в 5,0 раза больше 74 734. При линейном
масштабировании один проход ≈ 200 мс, а цикл «страница + `COUNT`» ≈ 400 мс. Это выше
порога 100 мс, поэтому вопрос нужно закрыть **измерением**, а не оценкой.

**Не измерено и требует замера (раздел 7):** стоимость на 350 000+ файлов (первая
страница, средняя, последняя, `COUNT`); поведение при холодном кэше ОС; отзывчивость
интерфейса во время подгрузки (время от нажатия до обновления дерева, отсутствие
залипания UI-потока при добавлении порции); стоимость построения/дополнения дерева
на 10 000 узлов.

**Схема индекса не меняется.** Если после замеров окажется, что стоимость неприемлема,
предлагается (за отдельным утверждением, как самостоятельный этап) индексная
поддержка подстроки — FTS5 с `tokenize='trigram'` или предвычисляемая колонка ключа
сортировки. Это изменение схемы и/или индексации и в текущую реализацию не входит.

### 4.10. Что остаётся без изменений

Алгоритмы индексации, схема БД, `Folders`/`VideoFiles`, предпросмотр и hover
scrubbing, drag-and-drop в Premiere Pro, открытие папок, кеш миниатюр — не
затрагиваются. Новые зависимости не требуются.

## 5. Предлагаемый UX

### 5.1. Утверждённые решения (сохраняются без изменений)

1. **Кнопка «Показать ещё»** — основной и единственный механизм расширения выдачи.
2. **Размер первой и последующих порций — 200** (первая — как сейчас).
3. **Точный счётчик общего количества совпадений** (из `COUNT`).
4. **Отдельный счётчик уже показанных совпадений** («показано M из N»).
5. **Древовидное представление сохраняется** — группировка по источнику, году,
   месяцу и папкам; выдача не превращается в плоский список.

### 5.2. Рассмотренные альтернативы

| Вариант | Для монтажёра | Производительность | Сложность |
|---|---|---|---|
| Автоподгрузка при прокрутке | список «течёт» сам, но на быстром флике загружается несколько порций | нагрузка непредсказуема в момент набора запроса | средняя (+ отмена, + дописывание без пересоздания контейнеров) |

Автоподгрузка при прокрутке остаётся возможным расширением после ручной приёмки и

### 5.3. Дополнения к утверждённой схеме

  (`MainWindow.xaml:819-996`), рядом со строкой `SearchResultsSummary`
  (`MainWindow.xaml:837-841`), и не участвует в прокрутке дерева.

## 6. План реализации небольшими проверяемыми шагами

Каждый шаг завершается зелёной сборкой и тестами; приложение остаётся рабочим после
каждого шага. Шаги 1-4 не видны пользователю и принимаются по тестам; шаг 5 требует
ручного просмотра. Все шаги допускают независимое ревью и откат.

**Шаг 0. Эталон и характеризующий тест.**
Зафиксировать текущие 255 тестов и результаты замеров (разделы 1.3, 1.4, 4.9) в
документации. Добавить характеризующий тест: синтетический индекс с 250
совпадениями, `SearchAsync` возвращает ровно 200 — тест документирует дефект.
Продуктив не меняется.

**Шаг 1. Контракт постраничного поиска (OFFSET/LIMIT).**
Добавить `FolderSearchSession`, `FolderSearchPage`, `IFolderSearchPageService`.
Реализовать `SqliteFolderSearchPageService` поверх существующих запросов с `OFFSET`,
распределением бюджета между потоками (раздел 4.3) и отдельными `COUNT`. Общие
построители SQL вынести в один внутренний помощник. UI не трогается.
Тесты: 0/1/199/200/201/1000/10000 совпадений; отсутствие дубликатов и пропусков при
переходах между порциями; равенство постраничной выборки одноразовой выборке без
лимита; корректность на глубоких страницах.

**Шаг 2. Совместимость старого API.**
`SqliteFolderSearchService.SearchAsync` реализуется через постраничный сервис
(первая порция). Все 255 существующих тестов остаются зелёными без правок. Добавить
тест, что потолок 1000 и валидация `MaxResults` сохранены.

**Шаг 3. Модель представления: счётчики и команда.**
`FolderSearchViewModel` получает `LoadMoreCommand`, `TotalMatchCount`,
`LoadedMatchCount`, `HasMoreResults`; `ResultsSummary` переходит на формат
«Найдено совпадений: N; показано M». Первая порция грузится как сейчас.
Тесты на подставном `IFolderSearchPageService`: быстрый набор текста отменяет
предыдущий запрос, устаревшая версия не попадает в дерево, счётчики корректны при
0/1/200/201 совпадениях.

**Шаг 4. Инкрементальное дерево и обёртка представления.**
`FolderSearchTreeItem` (INotifyPropertyChanged, `ObservableCollection` детей,
монотонный `IsMatch`, пересчёт `NameSegments` через `FolderNameHighlightService`) и
`FolderSearchTreeMerger`. Тесты: идемпотентность; эквивалентность одноразовому
`Build` при разных разбиениях на порции; переклассификация контекстного узла;
монотонность `IsMatch`; порядок детей; создание предков ровно один раз.

**Шаг 5. Интерфейс: кнопка, счётчики, пакетное дописывание.**
`MainWindow.xaml`: кнопка «Показать ещё» + строка счётчика; блокировка кнопки на
время загрузки; добавление порции одним пакетом на UI-потоке. `MainWindow.xaml.cs`:
активация узла и перетаскивание переводится на обёртку. Проверка: сценарий из отчёта
о дефекте — довести число показанных до 633 и найти
`10_15_ФестивальПамятиЕфремова_Лабецкая_03-23.mxf` в дереве.

**Шаг 6. CHANGE-STOP: отпечаток индекса.**
Сессионное read-only соединение; `PRAGMA data_version` — единственный источник
решения об остановке. Значение снимается в одной транзакции с порцией. При
расхождении — остановка подгрузки, сохранение дерева, подсказка. Тройка
`(COUNT, MAX(Id), MAX(LastSeenUtc))` по участвующим источникам — только диагностика
(какой источник изменился, запись в журнал) и **не отменяет** остановку. Тесты:
вставка, удаление, обновление на месте и переименование между порциями; при
обнаружении изменения дерево не меняется и следующая порция не выполняется; остановка
безусловна (в том числе когда тройка не изменилась).

**Шаг 7. Офлайн и режим соединения.**
Перевести соединение поиска в `ReadOnly`. Тест: поиск работает при недоступном
UNC-пути источника (база локальная); поиск не создаёт файл базы, если он отсутствует,
а возвращает понятное состояние.

**Шаг 8. Производительность на 350 000+.**
Расширить `SearchBenchmarkRunner.cs` (сейчас только папки, `FolderCount = 100_000`,
`:13`, `:136-141`) на видеофайлы и на постраничные сценарии: первая порция, средняя,
последняя, `COUNT`. Записать новый базовый замер в `SearchPerformanceBaseline.md`.
Отдельно — ручной замер отзывчивости интерфейса при подгрузке. По результату принять
или отклонить запасной вариант keyset и решение об индексной поддержке подстроки
(раздел 4.9).

## 7. План тестирования

### 7.1. Автоматические тесты

Новый файл (предлагаемое имя
`tests/VideoArchiveFinder.Tests/Search/SqliteFolderSearchPageServiceTests.cs`) и
дополнения к существующим.

**Границы количеств.** 0, 1, 199, 200, 201, 1000, 10 000 совпадений — точное общее
число, корректное `HasMore`, полная выборка за `ceil(N / pageSize)` порций без
пропусков и дубликатов (сравнение множества `Id` с одноразовой выборкой без лимита).
Для 10 000 дополнительно проверяется последняя и предпоследняя порция.

**Порядок и глубина.** Постраничная выборка строго равна выборке «всё за один раз»
для папок и для файлов по отдельности и в объединённой выдаче; проверка на глубине
10 000 строк; проверка распределения бюджета между потоками (27 папок + 173 файла).

**Несколько источников.** Один в режиме `FolderNames`, один в `VideoFileNames`, один
в `FolderAndVideoFileNames`; проверка, что файлы участвуют в поиске, а папки — по
режиму; характеризующий тест на расхождение «индексировано, но не ищется»
(раздел 9.2) как фиксация текущего поведения.

**Совпадения в папках и в файлах.** Объединение в одном дереве, приоритет «папки
первыми» сохранён, `FolderMatchCount` и `VideoMatchCount` в сумме дают
`TotalMatchCount`.

**Группировка.** Несколько совпадений в одной папке, разнесённые по разным порциям,
попадают под один узел-папку; узлы-предки создаются один раз.

**Переклассификация (требование ревью 4).** Папка приходит сначала как контекстный
узел, затем как совпадение: `IsMatch` становится `true`, `NameSegments` содержат
подсветку, узел не дублируется, дети и раскрытие сохраняются. Обратный порядок:
контекстный узел, пришедший после совпадения, не понижает `IsMatch` и не затирает
подсветку.

**Кириллица и словоформы.** `ЁЛК`/`ёлки`, смешанный регистр, подчёркивания и цифры
(`10_15_Фестиваль…`), словоформы `почта/почты/почтовый`, `дорога/дорожный`, два
токена (все должны совпасть), запрос короче 3 символов (режим точного токена),
символы `%` и `_` как литералы.

**Отмена и быстрый ввод.** 10 последовательных изменений текста — в дереве остаётся
только результат последнего; отменённая порция не добавляется; `Dispose` во время
загрузки не приводит к исключению; сессионное соединение закрывается.

**Отпечаток индекса (требование ревью 1).** По одному тесту на каждое событие
между порциями: вставка, удаление, обновление на месте, переименование (вставка +
удаление), удаление устаревших файлов папки, удаление устаревших папок, удаление
источника. Во всех случаях: следующая порция не выполняется, дерево не меняется,
счётчики сохраняются. Отдельные тесты на безусловность остановки: изменение
обнаруживается, даже когда диагностическая тройка осталась прежней; переиндексация
другого источника также останавливает подгрузку (ложное срабатывание признано
допустимым).

**Офлайн.** Поиск работает при недоступном UNC-пути; отсутствующий файл базы не
создаётся молча.

**Дерево.** Идемпотентность `FolderSearchTreeMerger`, эквивалентность `Build` при
всех разбиениях на порции, порядок детей, обработка циклов `ParentFolderId`.

## 8. Риски и открытые вопросы

### 8.1. Риск: расхождение выражений фильтра и сортировки (средний, снижен)

Для выбранного варианта A риск резко ниже, чем для keyset: форма запроса остаётся
сегодняшней, нет сравнения кортежа из выражений и нет второго места, где
повторяются `COLLATE NOCASE` и `CASE`. Остаётся требование, чтобы условие поиска и
`ORDER BY` строились **в одном месте** и одинаково использовались в выдаче и в
`COUNT`; проверяется тестом равенства постраничной и одноразовой выборки.

### 8.2. Риск: производительность на полном архиве (высокий, требует решения)

Измерено: цикл «страница + `COUNT`» ≈ 80 мс на самом крупном текущем источнике
(74 734 строки). Экстраполяция на 376 342 строки даёт ≈ 300-350 мс, что выше
действующего порога p95 ≤ 100 мс; порог установлен для поиска по папкам и
видеофайлы в нём не покрыты. Решение принимается **после** замера из раздела 7.3.
Варианты: (а) согласовать новый порог для поиска по файлам; (б) уменьшить число
`COUNT`; (в) отдельным утверждённым этапом добавить индексную поддержку подстроки
(схема индекса меняется только с отдельного разрешения).

### 8.3. Открытый вопрос: раскрытие узлов при виртуализации

`IsExpanded = True` задано стилем контейнера (`MainWindow.xaml:877-888`) при
включённой виртуализации с переработкой контейнеров. Известное поведение WPF: при
пересоздании контейнеров раскрытие не восстанавливается. Это **не** объясняет потерю
совпадений (она доказана усечением), но может объяснять, почему пользователь видел в
папке меньше файлов, чем в ней есть. Требуется ручная проверка (пункт 7.2.3) и, при
подтверждении, перенос `IsExpanded` в модель узла. Отдельного утверждения требует
сама правка, а не проверка.

### 8.4. Открытый вопрос: порядок детей при дописывании

Алфавитный порядок (как сейчас) означает вставки в середину уже отрисованного
списка при подгрузке. Альтернатива — порядок поступления (только дописывание в
конец), но это меняет нынешнее видимое поведение и существующие тесты. По умолчанию
сохраняется алфавитный порядок; автопрокрутка не выполняется.

### 8.5. Открытый вопрос: пороги UX

Размер порций 200 (утверждён), порог подсказки «совпадений много» — предлагается
5 000. Требует утверждения только порог подсказки.

### 8.6. Решения, требующие утверждения перед реализацией

1. **Вариант A (`OFFSET`/`LIMIT`) как основной** и keyset только как запасной при
   выполнении измеримого триггера. Это изменение по сравнению с первоначальным
   документом.
2. **Политика CHANGE-STOP** как окончательное поведение при изменении индекса:
   остановка подгрузки, сохранение показанного дерева, обновление только вручную.
3. **Отпечаток на `PRAGMA data_version`** с сессионным read-only соединением;
   остановка выполняется по нему безусловно, тройка
   `(COUNT, MAX(Id), MAX(LastSeenUtc))` используется только как диагностика.
   Альтернатива без сессионного соединения (только тройка как единственный механизм,
   ~37 мс на порцию, условная гарантия) — требует отдельного решения, если сессионное
   соединение нежелательно.
4. **Обёртка представления** `FolderSearchTreeItem` в слое Desktop (мутабельность
   `IsMatch`, `NameSegments`, `ObservableCollection` детей) и перевод активации узла
   и перетаскивания на неё.
5. **Готовность к тому, что p95 поиска по видеофайлам может превысить 100 мс**, с
   последующей отдельной задачей по индексной поддержке подстроки (изменение схемы
   индекса — только с отдельного разрешения).
6. **Согласие на изменение соединения поиска на `ReadOnly`** (раздел 4.8).
7. **Порядок работы с побочными дефектами** (раздел 9): подтвердить, что они остаются
   отдельными задачами и в эту реализацию не входят.

## 9. Побочные дефекты: отдельные задачи, вне текущей реализации

Все три найдены при проверке «нет ли иных причин потери совпадений». В текущем
индексе они не проявляются (раздел 2.5), исправление в эту реализацию **не входит**.

### 9.1. Молчаливый пропуск файлов при недоступной папке

`FolderIndexingService.IndexVideoFilesAsync` при `!folder.IsAvailable` возвращает
`(0, 0)` без инкремента счётчика ошибок
(`src/VideoArchiveFinder.Infrastructure/Indexing/FolderIndexingService.cs:368-373`), а
`SystemFolderTreeEnumerator` создаёт папку с `IsAvailable = false` при любом
исключении обхода (`SystemFolderTreeEnumerator.cs:78-90`). «Успешно завершённая»
индексация может не содержать файлы отдельных папок.

Отдельная задача: отражать такие папки в `FolderIndexingStates` или в журнале как
предупреждение о неполноте индекса.

### 9.2. Проиндексированные, но неучаствуемые в поиске файлы

Область поиска выводится из **объявленного** режима источника
(`MainWindowViewModel.cs:713-721`), а содержимое индекса — ещё и из **открытия
папок**: `FolderVideoFilesViewModel.cs:304` вызывает `IVideoFolderRefreshService`,
который безусловно записывает имена файлов
(`VideoFolderRefreshService.cs:40-136`) независимо от режима источника.

Измерено: источник `\\archive1\Массив_1_Видеоархив` имеет режим `FolderNames`, но в
индексе лежат **12 306** записей `VideoFiles` (при 277 различных путях папок с
файлами), и все они недостижимы для поиска. Отдельная задача: либо выводить область
поиска из содержимого индекса, либо не индексировать имена файлов для таких
источников, либо явно показывать это в интерфейсе выбора источника.

### 9.3. Гигиена индекса при удалении источника

`SqliteFolderIndexCleanupService.DeleteByRootSourceIdsAsync`
(`SqliteFolderIndexCleanupService.cs:22-143`) удаляет только `Folders` и
`FolderIndexingStates` — **`VideoFiles` не удаляются никогда**. Отдельная задача:
удалять строки видеофайлов при удалении источника и предусмотреть разовую очистку уже
накопившихся.

### 9.4. Разрешение противоречий в численных данных

Точная сверка (измерено, `mode=ro`):

| Источник | В `archive-sources.json` | Папок | Файлов | Строка в `FolderIndexingStates` |
|---|---|---:|---:|---|
| `2efc02e8-…` `\\archive1\Массив_1_Видеоархив`, режим `FolderNames` | да | 9 810 | 12 306 | да (2026-10-02) |
| `c2f3fd3b-…` `\\archive2\Сюжеты панорамы 2`, режим `VideoFileNames` | да | 672 | 74 734 | да (2026-10-02) |
| `e682f835-…` `\\archive1\Массив_1_Видеоархив` (ранняя регистрация) | нет | 9 704 | 618 | нет |
| `5376eadf-…` `\\archive1\…\!Заграница\Беларусь\2023_октя` | нет | 0 | 3 521 | нет |
| `98343618-…` `\\archive2\…\2025\05_МАЙ\…` | нет | 0 | 397 | нет |
| `69bdc87f-…` `D:\Malashkin\Project\…` | нет | 0 | 155 | нет |
| `28466fcf-…` `D:\Malashkin\Project\…` | нет | 0 | 101 | нет |
| `b5dff022-…` `\\archive1\…\Транспорт_Дороги\Большегрузы\…` | нет | 0 | 19 | нет |
| **Итого** | 2 | **20 186** | **91 851** | 2 |

Сверка сходится точно: 9 810 + 672 + 9 704 = 20 186 папок и
74 734 + 12 306 + 4 811 = 91 851 файл (4 811 = 618 + 3 521 + 397 + 155 + 101 + 19).

Разрешённые противоречия:

1. **Удалённых источников шесть, а не пять**, как было указано в первоначальном
   документе; суммарно 4 811 строк `VideoFiles` и 9 704 строки `Folders`.
2. **Отсутствие строки в `FolderIndexingStates` не является следом очистки.**
   Строка состояния записывается только после **полностью завершённого** обхода
   (`FolderIndexingService.cs:250-288`); ветви отмены и исключения её не пишут
   (`:299-318`), а пакеты папок к этому моменту уже зафиксированы. Значит, у всех
   шести удалённых источников полного обхода не было.
3. **Почему сохранились 9 704 строки папок.** Путь удаления
   (`MainWindowViewModel.cs:560-575`) сначала вызывает очистку индекса и только потом
   перезаписывает список источников, поэтому «источник исчез из JSON, а строки
   остались» означает, что очистка для него не сработала. Наиболее правдоподобное
   объяснение: источник `e682f835-…` был удалён сборкой старше коммита `6b69f0e`
   (`feat: clean folder index when removing sources`, 28 июля 2026), то есть до
   появления очистки; первый коммит проекта — 21 июля 2026. Косвенно это
   подтверждается тем, что `e682f835-…` указывает на **тот же корень**
   `\\archive1\Массив_1_Видеоархив`, что и действующий `2efc02e8-…`, а число папок
   близко (9 704 против 9 810) — это повторная регистрация одного архива.
4. **Почему у пяти источников нет папок, но есть файлы.** Их папки не «потерялись при
   очистке»: строки `Folders` создаются только полным обходом, а `VideoFiles` —
   также и при открытии папок (`VideoFolderRefreshService`). Источник, который
   добавили, прошли браузером и удалили, не запуская полный обход, оставляет ровно
   такую картину: 0 строк `Folders`, 0 строк состояния, N строк `VideoFiles`.
   И поскольку очистка не удаляет `VideoFiles` (раздел 9.3), строки файлов остаются.

Что осталось недоказуемым по индексу: точная причина, по которой очистка не сработала
для `e682f835-…` (отсутствие функции на момент удаления, прерывание процесса или
иная причина). Проверочный шаг, закрывающий вопрос: удалить тестовый источник через
интерфейс и убедиться, что строки `Folders` исчезают, а `VideoFiles` — нет (что и
подтвердит необходимость задачи 9.3). Стоимость найденного мусора — измеряемая часть
файла индекса 109 064 192 байт; отдельный учёт его доли не проводился.

## Приложение B. Как воспроизводились замеры

База индекса открывалась только на чтение:

```python
sqlite3.connect("file:<путь>/video-archive-finder.db?mode=ro", uri=True)
```

SQL-текст запросов по папкам и по видеофайлам, включая условия «умного» поиска,
`ORDER BY`, `LIMIT`, соединение с `Folders` и слияние с приоритетом папок,
воспроизведён дословно по `SqliteFolderSearchService`. Времена — медиана 10 прогонов
после 5 прогревов на локальном файле с тёплым кэшем ОС.

Семантика `PRAGMA data_version` проверена на **отдельной временной базе** в `%TEMP%`
с двумя соединениями (читатель в `mode=ro` и писатель); временная база удалена после
проверки.

Скрипты зонда лежат вне репозитория, в `%TEMP%`: `vaf_probe.py`, `vaf_probe2.py`
(состав индекса и воспроизведение усечённой выдачи), `vaf_probe3.py` (латентные
причины), `vaf_probe4.py` (строки по источникам), `vaf_probe5.py` (ранг файла и классы
приоритета), `vaf_probe6.py` (точная сверка по источникам), `vaf_plan.py` (планы
запросов), `vaf_bench.py` (стоимость страниц, `COUNT`, отпечатка),
`vaf_dataversion.py` (глубокие смещения и семантика `data_version`). Данные архива и
база индекса не изменялись.
