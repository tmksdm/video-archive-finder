## 1. Подтверждённая причина дефекта

### 1.1. Кратко

Дефект — **усечение выдачи до построения дерева**. Поиск физически находит 633
совпадения по запросу `фестиваль`, но пользователю доступны только 200 — причём
это 200 первых записей по внутреннему порядку, который не совпадает с
ожиданиями монтажёра. Файл
`10_15_ФестивальПамятиЕфремова_Лабецкая_03-23.mxf` находится в индексе, доступен
(`IsAvailable = 1`), но его позиция в этом порядке — 458-я из 606
совпадений по видеофайлам, поэтому он не попадает в окно. Контрольный запрос
`фестивальПамяти` сужает множество кандидатов и потому находит файл.

Иных причин потери совпадений в текущем индексе **не обнаружено** (разделы 2.5-2.7):
все проверенные «латентные» механизмы дают нулевой вклад.

### 1.2. Цепочка кода

1. Жёсткая константа в модели представления, определяющая размер запроса:

   - `src/VideoArchiveFinder.Desktop/ViewModels/FolderSearchViewModel.cs:12` —
     `private const int MaximumDisplayedResults = 200;`
   - `src/VideoArchiveFinder.Desktop/ViewModels/FolderSearchViewModel.cs:185-190` —
     эта константа передаётся как `MaxResults` в `FolderSearchQuery`.

2. Отдельный `LIMIT` для папок и для видеофайлов:

   - `src/VideoArchiveFinder.Infrastructure/Search/SqliteFolderSearchService.cs:471` —
     `LIMIT $maxResults;` в запросе по `Folders`.
   - `src/VideoArchiveFinder.Infrastructure/Search/SqliteFolderSearchService.cs:244` —
     `LIMIT $maxResults;` в запросе по `VideoFiles`.
   - `src/VideoArchiveFinder.Infrastructure/Search/SqliteFolderSearchService.cs:85-108` —
     оба запроса выполняются независимо, затем результат объединяется.

3. Ограничение объединённого результата — уже **после** обоих `LIMIT`:

   - `src/VideoArchiveFinder.Infrastructure/Search/SqliteFolderSearchService.cs:322-342` —
     `MergeResults`: сначала идут все совпадения по папкам, затем по файлам,
     накопление прекращается при достижении `maxResults` (`:335-338`).
     Для воспроизведения это значит: 27 папок + 173 файла = 200, из бюджета
     выдачи 13,5 % расходуется на совпадения из **другого** источника.

4. Счётчик показывает усечённое число как общее:

   - `src/VideoArchiveFinder.Desktop/ViewModels/FolderSearchViewModel.cs:222-224` —
     `$"Найдено результатов: {matches.Count}"`, где `matches` — уже урезанный
     список. Отсюда «Найдено результатов: 200» в отчёте о дефекте.

5. Порядок, из-за которого «длинные» имена уходят за границу окна.
   Для видеофайлов (`SqliteFolderSearchService.cs:234-243`) и для папок
   (`:449-472`) сортировка одинаковая:

   ```
   CASE … END,                 -- приоритет: точное равенство → префикс → вхождение → прочее
   length(Name),               -- ← КОРОТКИЕ ИМЕНА ИДУТ ПЕРВЫМИ
   Name COLLATE NOCASE,
   Id
   ```

   Приоритетный класс здесь не разделяет совпадения: замер показал, что **все 606**
   найденных файлов имеют класс 2 (подстрока найдена, но не с начала имени). Поэтому
   фактически порядок определяет `length(Name)`: `10_15_ФестивальПамятиЕфремова_Лабецкая_03-23.mxf`
   имеет длину 48 символов, и перед ним оказывается 457 совпадений с более
   короткими именами.

6. Косвенное подтверждение того, что «просто увеличить константу» недостаточно:

   - `SqliteFolderSearchService.cs:13` — `MaximumAllowedResults = 1000`;
   - `SqliteFolderSearchService.cs:576-584` — значение `MaxResults` больше 1000
     отвергается с `ArgumentOutOfRangeException`;
   - `tests/VideoArchiveFinder.Tests/Search/SqliteFolderSearchServiceTests.cs:514-528` —
     это поведение закреплено тестом (`[InlineData(0)]`, `[InlineData(1001)]`).

   То есть потолок 200 задан в двух местах, и второй из них — «архитектурный»
   предел в сервисе.

### 1.3. Измерения на реальном индексе

Скрипт-зонд (read-only, `sqlite3` из Python) воспроизвёл SQL сервиса дословно,
включая условия «умного» поиска, `ORDER BY` и лимиты.

Состав индекса:

| Показатель | Значение |
|---|---:|
| Всего строк в `Folders` | 20 186 |
| Всего строк в `VideoFiles` | 91 851 |
| `\\archive2\Сюжеты панорамы 2` (режим `VideoFileNames`) | 672 папки, 74 734 файла |
| `\\archive1\Массив_1_Видеоархив` (режим `FolderNames`) | 9 810 папок, 12 306 файлов |

Запрос `фестиваль` (умный поиск, оба источника включены):

| Показатель | Значение |
|---|---:|
| Совпадений по папкам (без лимита) | 27 |
| Совпадений по именам файлов (без лимита) | **606** |
| Итого совпадений | **633** |
| Отдано запросом по папкам (`LIMIT 200`) | 27 |
| Отдано запросом по файлам (`LIMIT 200`) | 200 |
| Показано после `MergeResults` | **200** (27 папок + 173 файла) |
| Файлов в `2025\10_ОКТЯБРЬ`, совпадающих с запросом | **17** |
| Из них попало в показанные 200 | 5 |

Поскольку 27 мест в бюджете занимают совпадения по папкам, из 606 файлов до экрана
доходят только первые 173 по порядку сортировки. Окно обрывается на файле
`05_10_Фестиваль_Белая_чайка_Сомкина.mp4`, а всё, что отсортировалось позже, за
границей окна. Поэтому в `2025\10_ОКТЯБРЬ` видна лишь малая часть из 17 совпадений
(замер дал 5; при варианте, когда 200 мест достаются только файлам без совпадений
по папкам, — 8). Пользователь наблюдал в этой папке «только два файла»; точное
видимое число зависит от момента наблюдения и от того, какие узлы дерева успели
раскрыться, но существенно здесь не оно, а то, что из 633 совпадений по запросу
доступны ровно 200.

Файл из отчёта о дефекте:

```
Name          : 10_15_ФестивальПамятиЕфремова_Лабецкая_03-23.mxf
NormalizedName: 10_15_фестивальпамятиефремова_лабецкая_03-23.mxf
FolderFullPath: \\archive2\Сюжеты панорамы 2\2025\10_ОКТЯБРЬ
IsAvailable   : 1
length(Name)  : 48
```

Позиция в порядке выдачи: **458-я из 606**. Это полностью объясняет, почему файл
не виден в общей выдаче и находится контрольным запросом.

### 1.4. Проверка производительности: `LIMIT` не экономит работу

`EXPLAIN QUERY PLAN` для запроса по видеофайлам:

```
SEARCH v USING INDEX IX_VideoFiles_RootSourceId_FolderFullPath (RootSourceId=?)
SEARCH f USING COVERING INDEX UX_Folders_RootSourceId_FullPath (RootSourceId=? AND FullPath=?)
USE TEMP B-TREE FOR ORDER BY
```

Замеры (прогретый кэш, 3 прогона, тот же файл индекса):

| Сценарий | Время |
|---|---:|
| Запрос по видеофайлам с `LIMIT 200` | 39,3 мс |
| `COUNT(*)` по тому же условию, без лимита | 30,8 мс |

`instr()` не может использовать `IX_VideoFiles_NormalizedName`
(`SqliteVideoFileSchemaMigration.cs:65-70`), поэтому выполняется полный проход по
строкам источника и сортировка во временном B-дереве. **`LIMIT` применяется уже
после сортировки и не сокращает ни сканирование, ни сортировку.** Отсюда важное
следствие для проектирования: постраничная загрузка не обязана «спасать»
производительность SQL — она нужна для полноты и для объёма работы .NET/WPF.

## 2. Архитектурные ограничения текущего решения

### 2.1. Нормализация и морфология

- `TextNormalizationService` (`src/VideoArchiveFinder.Application/Search/TextNormalizationService.cs`):
  `FormC` → `trim` → `ToLowerInvariant` → `ё → е` → схлопывание пробелов.
  Дополнительно `Tokenize` делит строку по всем не-буквам/не-цифрам, поэтому
  `_`, `-`, `.` и цифры работают как разделители.
- `RussianSearchStemService` (`RussianSearchStemService.cs`): список окончаний плюс
  таблица «родственных» фрагментов; минимальная длина основы 3.
- Папки хранят предвычисленные `SearchTokens` и `SearchStems`
  (`SqliteIndexDatabaseInitializer.cs:209-210`), у видеофайлов таких колонок нет —
  «умный» поиск по файлам выполняет `instr` по `NormalizedName`
  (`SqliteFolderSearchService.cs:275-320`). Асимметрия объясняет, почему для файла
  `10_15_Фестиваль…` работает поиск подстроки, но нет отдельного учёта токенов.
  На полноту текущей выдачи эта асимметрия не влияет.

### 2.2. Объединение папок и файлов

- Папки: `BuildSelectCommand` по таблице `Folders` (`:417-475`).
- Файлы: запрос с `INNER JOIN Folders` по `(RootSourceId, FullPath = FolderFullPath)`
  (`:212-245`), идентификатор результата — **отрицательный** `-v.Id` (`:215`),
  чтобы не пересекаться с положительными идентификаторами папок.
- `MergeResults` (`:322-342`) дедуплицирует по `Id`; поскольку пространства
  идентификаторов не пересекаются, схлопывания разных объектов не происходит.
  Порядок — «сначала папки, затем файлы», усечение — по общему счётчику.

Область поиска задаётся **двумя независимыми** наборами идентификаторов
(`FolderSearchQuery.RootSourceIds` и `VideoFileRootSourceIds`), которые
формируются в `MainWindowViewModel.UpdateSearchSourceFilter`
(`src/VideoArchiveFinder.Desktop/ViewModels/MainWindowViewModel.cs:707-732`) из
**объявленного режима индексации** каждого источника
(`ArchiveSourceIndexingMode`, `src/VideoArchiveFinder.Domain/ArchiveSources/ArchiveSourceIndexingMode.cs`).

### 2.3. Построение дерева

`FolderSearchTreeBuilder.Build`
(`src/VideoArchiveFinder.Application/Search/FolderSearchTreeBuilder.cs:15-93`):

1. словарь папок = контекстные папки (рекурсивный CTE
   `SqliteFolderSearchContextProvider.cs:54-115`, поднимающийся от
   `NavigationFolderId`/`Id` совпадения к корню) + сами совпадения (`:30-39`);
2. `FindIncludedFolderIds` (`:95-123`) добавляет всех предков каждого совпадения —
   поэтому в дереве есть узлы-«обёртки», которые не являются совпадениями
   (`IsMatch = false`);
3. дети раскладываются по `ParentFolderId`, корни и дети сортируются
   `Name OrdinalIgnoreCase`, затем `FullPath` (`:78-92`, `:140-160`);
4. узлы создаются рекурсивно с защитой от циклов (`:125-193`).

Ключевое ограничение: **`Build` принимает уже полный набор совпадений**. Он
вызывается ровно один раз на запрос
(`FolderSearchViewModel.cs:203-208`), и на его входе уже лежит усечённый список.
Модель «постепенной загрузки» в нынешнем виде не поддерживается — потребуется
инкрементальное добавление (раздел 4.4).

### 2.4. Виртуализация интерфейса

`SearchResultsTree` — `TreeView` с `VirtualizingPanel.IsVirtualizing="True"` и
`VirtualizationMode="Recycling"` (`MainWindow.xaml:844-854`),
`ScrollViewer.CanContentScroll="True"`. Шаблон иерархический
(`MainWindow.xaml:890-994`), состояние раскрытия задаётся **стилем контейнера**:
`<Setter Property="IsExpanded" Value="True"/>` (`MainWindow.xaml:877-888`).

Из этого следуют два вывода:

- Объекты узлов создаются **все сразу** в `FolderSearchTreeBuilder.Build`, до
  отрисовки: виртуализация панели сокращает число визуальных элементов, но не
  число объектов-узлов, поэтому память определяется числом совпадений, а не
  видимой областью.
- Раскрытие не связано с данными. При пересоздании контейнеров
  (а пересборка дерева на новой странице их пересоздаёт) раскрытие и прокрутка
  теряются. Это аргумент в пользу **дописывания** узлов, а не пересборки
  (раздел 4.4), и одновременно гипотеза о причинах наблюдения «видно только два
  файла» (раздел 8.3).

Также важно для совместимости: активация узла открывает папку в правой панели и
выделяет файл (`MainWindow.xaml.cs:1193-1233`), перетаскивание начинается с
`TryStartFolderDrag` (`MainWindow.xaml.cs:1301-1348`). Оба сценария работают с
`FolderSearchTreeNode` и должны быть сохранены без изменений.

### 2.5. Что проверено дополнительно и **не** является причиной дефекта

Каждый механизм проверен по индексу; вклад — нулевой.

| Проверка | Результат | Вывод |
|---|---|---|
| Папки с `IsAvailable = 0` | 0 | нет пропусков из-за недоступных папок |

### 2.6. Латентно: проиндексированные, но неучаствуемые в поиске файлы

Область поиска выводится из **объявленного** режима источника
(`MainWindowViewModel.cs:713-721`), а содержимое индекса — ещё и из **открытия
папок**: `FolderVideoFilesViewModel.cs:304` вызывает
`IVideoFolderRefreshService.RefreshAsync`, который безусловно записывает имена
файлов (`VideoFolderRefreshService.cs:40-136`) независимо от режима источника.

Измерение: источник `\\archive1\Массив_1_Видеоархив` имеет режим `FolderNames`,
но в индексе лежат **12 306** записей `VideoFiles`. Поскольку этот источник не
попадает в `VideoFileRootSourceIds`, эти 12 306 файлов **недостижимы для поиска**,
хотя занимают индекс. Пользователь может это исправить переключением режима, но
само расхождение «что проиндексировано» и «что ищется» — дефект.

### 2.7. Латентно: гигиена индекса и удалённые источники

- `SqliteFolderIndexCleanupService.DeleteByRootSourceIdsAsync`
  (`src/VideoArchiveFinder.Infrastructure/Indexing/SqliteFolderIndexCleanupService.cs:22-143`)
  удаляет только `Folders` и `FolderIndexingStates` — **`VideoFiles` не удаляются**.
- Измерение: в индексе присутствуют данные **6 отсутствующих** источников —
  3 521 + 618 + 397 + 155 + 101 + 19 = 4 811 строк `VideoFiles` и 9 704 строки
  `Folders` (источник `e682f835-…`), тогда как в `archive-sources.json` остались
  два источника. Итог: 109 МБ базы и «мусор», который потенциально может попасть
  в выдачу, если когда-нибудь будет вызван поиск с `RootSourceIds = null`
  (`SqliteFolderSearchService.cs:441-447` такую ветку поддерживает).
- `FolderIndexingService.IndexVideoFilesAsync` при `!folder.IsAvailable`
  возвращает `(0, 0)` без инкремента счётчика ошибок
  (`src/VideoArchiveFinder.Infrastructure/Indexing/FolderIndexingService.cs:368-373`),
  а `SystemFolderTreeEnumerator` создаёт папку с `IsAvailable = false` при любом
  исключении обхода (`SystemFolderTreeEnumerator.cs:78-90`). В результате
  «успешно завершённая» индексация может молча не содержать файлы отдельных
  папок. В текущем индексе таких папок нет, но механизм существует.

## 3. Рассмотренные варианты исправления

Общие требования: доступ ко всем совпадениям; раздельные счётчики «всего» и
«загружено»; неблокирующая загрузка; сохранение дерева; стабильный порядок;
корректное объединение папок и файлов; отсутствие устаревшей выдачи; работа
офлайн; отсутствие «загрузить всё в память ради отрисовки»; учёт изменения
индекса между порциями.

### Вариант A. `OFFSET`/`LIMIT`

Простейшее решение: тот же упорядоченный запрос, `LIMIT $pageSize OFFSET $n`.

Плюсы: минимальные изменения; ключ сортировки уже детерминирован благодаря
финальному `Id`.

Минусы: повторное выполнение полного сканирования и сортировки на каждую
страницу (измерено ~39 мс на 74,7 тыс. файлов, то есть стоимость страницы не
зависит от её номера, но `OFFSET` в SQLite во временном B-дереве дополнительно
заставляет пропускать `n` строк); **появление дубликатов и пропусков**, если
индекс изменился между страницами (требование 10); общее число совпадений всё
равно требует отдельного `COUNT`.

### Вариант B. Keyset (seek) pagination

Условие «строго после курсора» по тому же кортежу, что и `ORDER BY`:

```sql
-- псевдокод
WHERE <условие поиска> AND <область>
  AND (Priority, length(Name), Name COLLATE NOCASE, Id) > (?, ?, ?, ?)
ORDER BY Priority, length(Name), Name COLLATE NOCASE, Id
LIMIT $pageSize
```

Плюсы: ни дубликатов, ни пропусков при неизменном индексе; стоимость страницы
не растёт с номером; **не нужно держать совпадения в памяти** — курсор это
десятки байт (прямое выполнение требования 9); детерминированный тотальный
порядок обеспечивается уникальным `Id`.

Минусы: `instr()` и вычисляемый `Priority` всё равно требуют полного прохода и
временного B-дерева — выигрыша по времени против варианта A нет; сравнение
кортежа expressions чувствительно к коллации и к точному повторению выражений
сортировки (главный риск, см. раздел 8.1); SQLite должен поддерживать row values
(3.15+; у `Microsoft.Data.Sqlite` встроена существенно более новая версия, но это
нужно закрепить тестом).

### Вариант C. Серверная «сессия поиска» (кеш упорядоченных кандидатов)

Один раз выполнить поиск, сохранить упорядоченный список кандидатов в сервисе под
ключом (версия запроса + текст + режим + источники) и отдавать страницы срезом.

Плюсы: одна дорогая операция на запрос; идеально стабильная выдача (snapshot);
простой счётчик.

Минусы: количественная оценка памяти. Запись-кандидат ~150-250 байт, 376 342 файла
из замера 1 сентября 2026 → десятки мегабайт на один запрос; это прямо
противоречит требованию 9 и плохо сочетается с debounce при наборе текста, когда
запросы создаются на каждый символ. Дополнительно требуется инвалидация по
изменению индекса.

Модификация C′ (сохранять только **ключи** сортировки, содержимое догружать
пачками по `Id`) снижает память в 4-5 раз, но не устраняет её полностью и
усложняет код.

### Вариант D. Гибрид: keyset-страницы + точный `COUNT` + межпоточный «слив» папок/файлов

Совмещает B с честным счётчиком и сохраняет нынешний приоритет «папки, затем
файлы»: два независимых курсора (папки и файлы), страница набирается из курсора
папок, затем из курсора файлов; общее число = сумма двух `COUNT`.

Плюсы: все требования 1-3, 5, 6, 9 выполняются без кеша совпадений; поведение
совпадает с текущим (папки первыми); изменение индекса обнаруживается штампом и
не приводит к порче выдачи.

Минусы: два запроса на страницу плюс один-два `COUNT` (измерено ~31 мс на
`COUNT` по 74,7 тыс. файлов — на полном архиве вырастет, см. риск 8.2);
необходимость аккуратной работы с коллацией.

### Сравнение

| Критерий | A. OFFSET/LIMIT | B. Keyset | C. Сессия | D. Гибрид |
|---|---|---|---|---|
| Полнота доступа | да | да | да | да |
| Дубликаты при изменении индекса | возможны | нет | нет | нет |
| Память на «все совпадения» | нет | нет | десятки МБ | нет |
| Стоимость страницы | O(offset) + скан | скан+сорт | O(1) | скан+сорт |
| Точный общий счётчик | отдельный запрос | отдельный запрос | бесплатно | отдельный запрос |
| Объём изменений | малый | средний | средний | средний |
| Требование 9 («не грузить всё в память») | да | да | **нарушено** | да |

**Рекомендация: вариант D** (keyset + `COUNT` + раздельные курсоры папок и
файлов). Вариант C отклонён из-за требования 9 и из-за debounce; вариант A — как
единственный механизм из-за дубликатов при изменении индекса (но `OFFSET` можно
оставить в тестах как эталон для проверки ключей сортировки, раздел 7).

## 4. Рекомендуемая архитектура

### 4.1. Новый контракт вместо изменения существующего

Чтобы не ломать 255 существующих тестов и вызовы, добавляется постраничный
контракт, а старый становится его частным случаем.

```
Application/Search/FolderSearchCursor.cs      // Kind, Priority, Length, Name, Id
Application/Search/FolderSearchPage.cs        // Matches, TotalMatchCount,
                                              // LoadedMatchCount, HasMore,
                                              // FolderMatchCount, VideoMatchCount,
                                              // NextCursor, IndexStamp
Application/Search/IFolderSearchPageService.cs
Infrastructure/Search/SqliteFolderSearchPageService.cs
```

- `IFolderSearchService.SearchAsync` остаётся и реализуется как «первая страница
  с `MaxResults`» через новый сервис — поведение и тесты сохраняются.
- Общие построители SQL (условие «умного» поиска, элементы `ORDER BY`,
  параметризация источников) выносятся в один внутренний помощник, чтобы условия
  поиска и сортировки физически не могли разойтись между «точечным» и постраничным
  запросами. Это прямо снижает риск 8.1.

### 4.2. Постраничный запрос

```sql
WITH Candidates AS (
    SELECT Id, FullPath, Name, NormalizedName, ParentFolderId, RootSourceId,
           IsAvailable, DirectSubfolderCount, DirectVideoFileCount,
           CASE WHEN NormalizedName = $normalizedQuery THEN 0
                WHEN instr(NormalizedName, $normalizedQuery) = 1 THEN 1
                WHEN instr(NormalizedName, $normalizedQuery) > 0 THEN 2
                ELSE 3 END AS Priority
    FROM Folders
    WHERE <условие поиска>
      AND RootSourceId IN (…)
)
SELECT … FROM Candidates
WHERE $hasCursor = 0
   OR (Priority, length(Name), Name COLLATE NOCASE, Id)
      > ($cursorPriority, $cursorLength, $cursorName COLLATE NOCASE, $cursorId)
ORDER BY Priority, length(Name), Name COLLATE NOCASE, Id
LIMIT $pageSize;
```

Для первой страницы `$hasCursor = 0`; для последующих — 1 и заполненные
параметры курсора. `NULL`-курсор в сравнении кортежей дал бы `NULL` (не `TRUE`) и
отфильтровал бы все строки, поэтому развилка на первом условии обязательна.

Для видеофайлов — та же форма с `v.Name`, `v.NormalizedName` и `INNER JOIN
Folders`. `Name COLLATE NOCASE` указывается **и** в `ORDER BY`, **и** в сравнении
кортежа — иначе `NOCASE` не применится к третьему элементу и порядок разойдётся.

Отдельно выполняется один `COUNT`-запрос на вид (папки и файлы), возвращающий
точное общее число совпадений. Как оптимизацию на будущее можно рассмотреть
`COUNT(*) OVER ()` в том же запросе, но не в первой версии: оконная функция
заставляет SQLite материализовать все подходящие строки.

### 4.3. Счётчики и состояния

Модель представления получает:

- `TotalMatchCount` — точное число совпадений (из `COUNT`);
- `LoadedMatchCount` — сколько узлов-совпадений уже в дереве;
- `HasMoreResults` — есть ли следующая страница;
- `ResultsSummary` — «Найдено совпадений: 633; показано 200».

Требование 2 выполняется буквально: общее число и загруженное число — разные
величины, и вторая честно растёт по мере подгрузки.

### 4.4. Инкрементальное дерево (главная новая часть)

Вместо «построить дерево целиком из полного набора» — **дописывание**:

`FolderSearchTreeMerger.Apply(existing, pageMatches, pageContextFolders)`:

1. для каждого нового совпадения поднять цепочку предков (данные берутся из уже
   загруженного контекста страницы; при отсутствии узла-предка создаётся
   узел-обёртка с `IsMatch = false` — так же, как это делает `Build`);
2. если узел с таким `Id` уже есть — переиспользовать существующий объект, а не
   создавать новый (иначе теряется состояние контейнера и позиция прокрутки);
3. нового ребёнка вставлять в позицию, соответствующую компаратору
   `Name OrdinalIgnoreCase`, затем `FullPath` — тот же порядок, что и в `Build`
   (`FolderSearchTreeBuilder.cs:78-92`, `:140-160`);
4. совпадения, уже присутствующие в дереве, игнорировать (идемпотентность).

Свойства, которые нужно закрепить тестами: идемпотентность (повторное применение
той же страницы не меняет дерево), равенство результата пошагового построения
одноразовому `Build` при любом разбиении на страницы, корректная группировка
«источник → год → месяц → папки» при попадании файлов одной папки в разные
страницы, отсутствие дубликатов узлов.

`FolderSearchTreeBuilder.Build` при этом не переписывается: он остаётся для первой
страницы и продолжает использоваться существующими тестами. `Merger`
реализуется поверх тех же правил и отдельно тестируется на эквивалентность
`Build`.

### 4.5. Изменение индекса между страницами (требование 10)

Выдача постраничного сервиса несёт `IndexStamp` — отпечаток состояния индекса по
участвующим источникам, например максимум `CompletedAtUtc` из
`FolderIndexingStates` для выбранных источников плюс максимум `LastSeenUtc` по
`VideoFiles` этих источников. Дешевле — по одному `SELECT MAX(...)` на источник.
`PRAGMA data_version` для этой цели не подходит: соединения создаются на каждый
вызов и закрываются, а `data_version` сравнивает состояние в рамках одного
соединения.

Поведение при расхождении штампа между страницами: **уже загруженные результаты
остаются на экране**, добавленные страницы продолжают дописываться по тем же
ключам сортировки (дубликатов не будет, так как `Id` уникален и порядок тотальный),
а в панели результатов появляется ненавязчивая подсказка «индекс обновился —
обновить результаты». Обновление — по явному действию пользователя.

Обоснование: список, который «перетасовывается» под курсором во время прокрутки,
для монтажёра хуже, чем слегка устаревший, но стабильный список. Автоматический
перезапуск поиска отвергнут.

### 4.6. Отмена, версионирование и офлайн

- Механизм `_searchVersion` + `CancellationTokenSource` уже реализован
  (`FolderSearchViewModel.cs:112-173`, `:210-213`, `:226-229`). Он
  распространяется на страницы: загрузка страницы несёт версию, результат
  устаревшей версии не добавляется в дерево (требование 7).
- Подгрузка страницы выполняется асинхронно, без блокировки UI; на время загрузки
  кнопка/индикатор блокируется, дерево остаётся отзывчивым (требование 3).
- Поиск обращается только к локальному файлу SQLite, сеть в пути поиска не
  участвует. Рекомендуется перевести соединение поиска с
  `ReadWriteCreate` (`SqliteFolderSearchService.cs:495-509`) на `ReadOnly`: сейчас
  поиск открывает базу на запись и **создаёт пустую базу**, если файл потерян, —
  это лишний риск и лишние права. Провайдер контекста уже работает в `ReadOnly`
  (`SqliteFolderSearchContextProvider.cs:159-173`). Требование 8 дополнительно
  закрепляется тестом: поиск по существующему локальному индексу работает при
  недоступном UNC-пути источника.

### 4.7. Что остаётся без изменений

Алгоритмы индексации, схема БД, `Folders`/`VideoFiles`, предпросмотр и hover
scrubbing, drag-and-drop в Premiere Pro, открытие папок, кеш миниатюр — не
затрагиваются. Новые зависимости не требуются: всё строится на SQLite, который уже
используется, и на существующих типах.

## 5. Предлагаемый UX

Рассмотренные варианты:

| Вариант | Для монтажёра | Производительность | Сложность |
|---|---|---|---|
| Автоподгрузка при прокрутке | список «течёт» сам, но страницы догоняют прокрутку и на быстром флике загружается несколько порций | нагрузка непредсказуема в момент набора запроса | средняя (+ отмена, + дописывание без пересоздания контейнеров) |
| Кнопка «Показать ещё» | явный контроль: пользователь сам решает, когда расширять выдачу | ровно одна страница на нажатие | низкая |
| Пагинация со страницами | неприменима: навигация идёт по дереву «источник → год → месяц → папка», номера страниц не значат ничего и разрывают группировку | — | средняя |

**Основной вариант: кнопка «Показать ещё» с честным счётчиком.** Дополнительно:
строка состояния «Найдено совпадений: 633; показано 200», а при общем числе
совпадений выше порога (предлагается 5 000) рядом с кнопкой появляется подсказка
«совпадений много — уточните запрос», потому что реальная задача монтажёра —
найти конкретный файл, а не просмотреть все.

Почему так:

- первый экран появляется быстро и не зависит от того, закончил ли пользователь
  формулировать запрос; при наборе текста дорогие порции не запускаются;
- нажатие — естественная точка отмены и повод показать прогресс;
- группировка дерева сохраняется, потому что «страница» — это дописанные узлы, а
  не отдельный экран.

Автоподгрузка при прокрутке оставлена как **опциональное расширение** (после
ручной приёмки и утверждения): технически она возможна на той же основе, но
требует гарантий отсутствия пересоздания контейнеров и защиты от лавины запросов
при быстрой прокрутке. Начинать с неё не следует.

Кнопка размещается под деревом результатов внутри `SearchResultsPanel`
(`MainWindow.xaml:819-996`), рядом со строкой `SearchResultsSummary`
(`MainWindow.xaml:837-841`), и не участвует в прокрутке дерева.

## 7. План тестирования

### Автоматические тесты

Новый файл (предлагаемое имя
`tests/VideoArchiveFinder.Tests/Search/SqliteFolderSearchPageServiceTests.cs`) и
дополнения к существующим.

Границы количеств: 0, 1, 199, 200, 201, 1000, 10 000 совпадений — точное общее

пропусков и дубликатов (сравнение множества `Id` с одноразовым `SearchAsync`
без лимита).

Несколько источников: один в режиме `FolderNames`, один в `VideoFileNames`, один в
`FolderAndVideoFileNames`; проверка, что файлы участвуют в поиске, а папки — по

как характеризующий текущее поведение.

Совпадения в папках и в файлах: объединение в одном дереве, приоритет «папки
первыми» сохранён, `FolderMatchCount` и `VideoMatchCount` в сумме дают
`TotalMatchCount`.

Группировка: несколько совпадений в одной папке, разнесённые по разным страницам,
попадают под один узел-папку; узлы-предки создаются один раз.

Эквивалентность порядков: keyset-выборка постранично строго равна выборке
`ORDER BY … OFFSET` (эталон) на одном и том же наборе данных — основной тест
против дефектов курсора и коллации.

Кириллица и словоформы: `ЁЛК`/`ёлки`, смешанный регистр, подчёркивания и цифры
(`10_15_Фестиваль…`), словоформы `почта/почты/почтовый`, `дорога/дорожный`,
два токена (все должны совпасть), запрос короче 3 символов (режим точного
токена), символы `%` и `_` как литералы.

Отмена и быстрый ввод: 10 последовательных изменений текста — в дереве остаётся
только результат последнего; отменённая страница не добавляется; `Dispose` во
время загрузки не приводит к исключению.

Индекс и доступность: подмена `IndexStamp` между страницами не дублирует и не
теряет узлы; поиск работает при недоступном UNC-пути; отсутствующий файл базы не
создаётся молча.

Изменение данных между страницами: вставка/удаление строк между выборками
порций — без дубликатов; при удалении ранее показанного совпадения дерево не
разрушается.

Дерево: идемпотентность `FolderSearchTreeMerger`, равенство одноразовому `Build`
для всех разбиений на страницы, порядок детей, обработка циклов `ParentFolderId`.

Производительность: бенчмарк на 100 000 папок и на 350 000+ видеофайлов —
p95 первой страницы, страницы в середине и последней страницы; контрольный
порог из раздела 8.2.

### Ручные проверки

1. Сценарий дефекта: `\\archive2\Сюжеты панорамы 2`, умный поиск, `фестиваль` →
   счётчик «633; показано 200» → «Показать ещё» доводит до 633 →
   `2025\10_ОКТЯБРЬ` содержит все 17 совпадений, включая
   `10_15_ФестивальПамятиЕфремова_Лабецкая_03-23.mxf`.
2. Быстрый набор `фест` → `фести` → `фестиваль`: нет мигания устаревших
   результатов, счётчик соответствует последнему запросу.
3. Прерывание сети на середине работы: подгрузка новой страницы показывает
   понятную ошибку, уже загруженное дерево и поиск по индексу остаются рабочими.
4. Переиндексация источника при открытом дереве: появляется подсказка об
   обновлении, список не «прыгает» под курсором.
5. Регресс взаимодействий: одиночный щелчок по узлу-файлу открывает папку в правой
   панели и выделяет файл; перетаскивание узла в Premiere Pro; открытие папки
   двойным щелчком; предпросмотр и hover scrubbing.
6. Дерево при большом числе совпадений: раскрытие узлов, прокрутка, отсутствие
   «схлопывания» при подгрузке страницы, отзывчивость при 10 000 узлов.
7. Разные DPI и разрешения — на дереве результатов (пункт остаётся открытым с
   предыдущего RC).

## 8. Риски, открытые вопросы и решения, требующие утверждения

### 8.1. Риск: расхождение порядка и курсора (высокий)

Keyset-пагинация ломается молча, если сравнение кортежа не совпадает с `ORDER BY`
по коллации или по выражениям (`length(Name)` против `length(NormalizedName)`,
колонка `Name` без `COLLATE NOCASE` в схеме — `SqliteVideoFileSchemaMigration.cs:32`),
или если `Priority` вычисляется в двух местах по-разному. Это даёт именно тот
класс дефекта, от которого мы избавляемся: часть совпадений исчезает.

Меры: единый помощник, строящий и фильтр, и сортировку, и курсор; обязательный
тест эквивалентности keyset и `OFFSET`; сравнение счётчиков до и после пейджинга.
Требует обязательного ревью.

### 8.2. Риск: производительность на полном архиве (высокий, требует решения)

Замер 1 сентября 2026 фиксирует 376 342 видеофайла. По измеренной стоимости
полного прохода (`~31 мс` на 74,7 тыс. строк) один проход по 376 тыс. строк — это
порядка 150 мс, а «страница + `COUNT`» — около 300 мс. Это выше действующего
порога p95 ≤ 100 мс из `SearchPerformanceBaseline.md`, причём прежний замер этого
не показывает, потому что в нём нет видеофайлов вообще (только папки и лимит 200).

Требуется решение (одно из):

- принять новый порог для поиска по файлам и зафиксировать его измерением;
- снизить стоимость: добавить индексную поддержку подстроки (FTS5 с
  `tokenize='trigram'`) или предвычисляемую колонку ключа сортировки. Это
  изменение схемы и/или индексации, поэтому **сейчас не предлагается к
  реализации** — только как отдельный этап после утверждения и замера.

Промежуточно можно снизить число `COUNT`: считать общее число по требованию (при
первом нажатии «Показать ещё») либо оценивать его сверху. Это ухудшает требование
2, поэтому решение за пользователем.

### 8.3. Открытый вопрос: раскрытие узлов при виртуализации

`IsExpanded = True` задано стилем контейнера (`MainWindow.xaml:877-888`) при
включённой виртуализации. Известное поведение WPF: при пересоздании контейнеров
(пересборка дерева) раскрытие и позиция не восстанавливаются, а при определённых
комбинациях настроек виртуализации часть дочерних узлов может не отрисоваться.
Это **не** объясняет потерю совпадений в поиске (она доказана усечением), но может
объяснять, почему пользователь видел в папке меньше файлов, чем в ней есть.
Требуется ручная проверка (пункт 7.2 ручного плана) и, при подтверждении,
перевод `IsExpanded` на свойство модели узла. Решение о правке — только после
проверки.

### 8.4. Открытый вопрос: сколько результатов показывать сразу и порог «слишком много»

Предлагается первая порция 200 (как сейчас), размер последующих порций 200,
подсказка «уточните запрос» от 5 000 совпадений. Значения требуют утверждения.

### 8.5. Открытый вопрос: приоритет папок над файлами в бюджете страницы

Сейчас 27 совпадений-папок из другого источника занимают 13,5 % выдачи. Подход D
сохраняет это поведение. Альтернативы: независимые бюджеты для папок и файлов
либо приоритет источника, выбранного пользователем. Изменение видимого поведения,
поэтому **по умолчанию не меняем** и оставляем как открытый вопрос.

### 8.6. Отдельные дефекты, требующие отдельного решения (не входят в исправление усечения)

- **Индексировано, но не ищется** (раздел 2.6): 12 306 имён файлов источника в
  режиме `FolderNames` недостижимы для поиска. Варианты: выводить область поиска
  из содержимого индекса, либо не индексировать имена файлов для таких
  источников, либо показывать это в интерфейсе выбора источника.
- **Гигиена индекса** (раздел 2.7): `DeleteByRootSourceIdsAsync` не удаляет
  `VideoFiles`, в индексе остаются данные 5 удалённых источников (~4 792 файла и
  9 704 папки). Нужна политика очистки (при удалении источника / отдельной
  операцией обслуживания).
- **Молчаливый пропуск файлов** при `!folder.IsAvailable`
  (`FolderIndexingService.cs:368-373`) не увеличивает счётчик ошибок и не
  отражается в состоянии индексации. Стоит отражать такие папки в
  `FolderIndexingStates` или в журнале как предупреждение о неполноте.

### 8.7. Требует утверждения перед реализацией

1. Выбранный вариант архитектуры — **D** (keyset + `COUNT` + раздельные курсоры).
2. Выбранный UX — **кнопка «Показать ещё»**; автоподгрузка при прокрутке
   откладывается.
3. Поведение при изменении индекса — сохранять загруженный список и предлагать
   обновление вручную.
4. Готовность к тому, что p95 поиска по видеофайлам может превысить 100 мс, с
   последующей отдельной задачей по индексной поддержке подстроки.
5. Порядок работы с дефектами из раздела 8.6: включать их в эту задачу или
   выносить отдельно.
6. Согласие на изменение соединения поиска на `ReadOnly` (раздел 4.6).

## Приложение B. Как воспроизводились замеры

```python
sqlite3.connect("file:<путь>/video-archive-finder.db?mode=ro", uri=True)
```

SQL-текст запросов по папкам и по видеофайлам, включая условия «умного» поиска,

`vaf_probe4.py` (строки по источникам), `vaf_probe5.py` (ранг файла и классы
приоритета), `vaf_plan.py` (планы запросов и замеры). Данные архива и база
индекса не изменялись.
